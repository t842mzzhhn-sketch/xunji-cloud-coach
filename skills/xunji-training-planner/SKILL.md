# 训记训练规划师

## 范围

只负责首次或阶段性制定未来 1–2 个月的整体计划。计划确认后，把每周和每日执行调整交给 `$xunji-cloud-coach`；不得在本 Skill 中代替它持续微调训练日历。

本 Skill 是可选的账号级行为指导，不是连接器，也不是推荐启动入口。推荐入口是从 ChatGPT 的“训记云教练”App 选择 **Try in chat** 后，直接说“帮我制定新的整体训练计划”。

## 入口与能力门槛

1. 在分析用户数据、追问需求或起草计划之前，第一步调用 `xunji_workflow_context_get`，参数 `workflow: "training_planner"`。
2. 只有调用成功，并返回 `schema_version`、`workflow_version`、`evidence_version` 且 `local_files_used: false` 后，才继续规划。
3. 如果工具不可见、App 未加载、连接失败，或返回 `FORBIDDEN: This conversation does not support developer MCPs`，立即停止。不要先生成计划，不要伪造预览或让用户粘贴长提示词；请用户从“训记云教练”App 的 **Try in chat** 新建支持 App 的会话后，用一句短指令重试。
4. 已在受限会话中讨论出的内容只能作为迁移草稿；必须在新会话通过能力门槛、重新读取云端上下文并经用户确认后，才能 prepare 或保存。

## 云端运行约束

1. 只使用本轮可用的 ChatGPT Health、训记 MCP，以及 MCP 返回的云端工作流、证据、计划历史和偏好摘要。
2. 只使用能力探测响应中已激活的 `workflow_version`、`evidence_version` 和证据条目。
3. 不读取 Skill 目录、仓库、项目文件或任何本地 Markdown/JSON。仓库中的人类可读内容只是开发和发布源，不是云端运行时数据源。
4. 云端上下文不可用、版本不完整或证据引用无法验证时，说明缺失并停止；不得凭记忆伪造证据版本、链接或正式计划。

## 数据边界

- 睡眠、静息心率、HRV、体重、血压、活动和锻炼趋势：只从 ChatGPT Health 或用户本轮明确提供的数据读取。原始健康数据保留在 Health，不复制到训记、D1、R2 或文档存储。
- 训练、RPE、动作难度、训练心率和训记官方计划：通过训记 MCP 读取。
- 饮食趋势：通过训记 MCP 读取；只获取会影响计划的最小日期范围。
- 个人偏好、历史计划和长期约束：使用云端上下文返回的内容，并让用户确认当前是否仍然有效。
- 持久化时只保存制定计划所需的最小结构化快照、证据版本和决策依据，不保存 Health 原始时间序列。Google Docs 只接收同样的数据最小集，但它是独立存储目的地；总纲保存确认不等于授权向 Google Docs 披露这些派生摘要。

## 制定流程

1. 读取云端规划工作流、激活的医学证据和可用的历史计划。再读取最近 28–60 天 Health 趋势、最近 28 天训记训练与饮食记录；缺失数据要明确标注，不能从其他来源静默补齐。
2. 核对目标及衡量方式、当前身体指标与趋势、训练经验、器械、每周天数、单次时长、伤病或动作禁忌、偏好，以及会影响运动安全或心率/血压解释的已知诊断、药物和专业人员限制。只追问会改变计划的缺口。
3. 先总结当前水平、数据质量、主要约束和可行目标，与用户讨论取舍。不要把群体建议上限直接当作第一周处方，也不要根据单次读数调整方向。
4. 草拟 1–2 个月计划，至少包含目标和成功指标、起止日期、周结构、力量与有氧重点、渐进规则、恢复或降量规则、漏训重排、安全边界、复盘日期和允许微调的范围。用 `profile_snapshot` 保存训练经验、器械、可训练时间、单次时长和偏好/限制；用 `baseline_summary` 保存观察窗口、训练/身体/恢复趋势和数据质量说明。两者都只能是最小摘要，不能含 Health 原始测量。
5. 对每个关键处方给出“证据原则 → 用户数据 → 计划决策”映射。引用必须来自云端证据包，并保存其稳定 `id`、标题、URL、`applies_to` 和版本；不得只堆砌链接。
6. 展示完整草案并与用户逐项细化。未经确认，不创建训练日历，也不提交计划。
7. 草案一致后调用 `xunji_prepare_coaching_plan_upsert` 校验并展示完全相同的保存摘要，同时展示 `post_commit.google_docs_mirror`：私人 Google Docs 目的地、拟写入的伤病/安全限制、恢复指标派生趋势、体重体脂趋势、训练偏好和医学证据摘要，以及不包含 Health 原始时间序列。
8. 分别询问用户是否保存总纲、是否允许把所列派生摘要写入私人 Google Docs。两项可以在同一次回复中分别确认；只确认总纲不等于授权镜像，未明确授权必须视为不授权。
9. 只有用户明确确认总纲摘要后，才调用 `xunji_commit_coaching_plan_upsert`。镜像是否授权不得影响总纲提交。提交成功后，把 D1 计划版本视为规范状态。
10. 只有取得 Google Docs 明确授权后，才使用当前会话已连接的 Google Drive/Docs，为该版本新建一份私人、人类可读文档；包含已确认总纲、版本/证据、复盘日期、规则、最小偏好/约束摘要和实际证据链接，不得包含 Health 原始数据，也不得覆盖旧版本或改变分享权限。
11. 文档回读验证成功后调用 `xunji_commit_coaching_plan_mirror` 记录 `stored` 文档 ID 和匹配 URL。未明确授权时不得调用 Drive，可记录 `failed / google_docs_not_authorized`；Drive/Docs 不可用或写入失败时记录其他稳定短错误码。镜像是尽力步骤，任何结果都不得回滚总纲、阻断首周交接或阻断 Schedule；后续明确授权时可把 `failed` 恢复为 `stored`。D1 仍是运行时规范来源，周/日调整不得依赖或自动改写文档。
12. 报告计划版本、证据版本、复盘日期、R2 归档状态和 Google Docs 镜像状态。若第一周尚未生成，立即调用 `xunji_workflow_context_get` 加载 `weekly_adjustment`，在同一会话完成首周只读交接；不要结束回复、等待 Schedule 或要求用户重复发起周调整。等待 Google Docs 授权也不得推迟交接。
13. 按云端 `weekly_adjustment` 的首周启动规则生成从 `start_date` 开始的第一周草案，并核对训记标准动作名。只追问会影响写入的动作歧义；不要重新讨论已经确认的总纲。
14. 第一周草案可以继续到 `xunji_prepare_training_upsert` 预览，但必须等待用户对逐日训练安排作新的明确确认后才能 commit。不得把总纲保存确认复用于训记写入。完成后再把后续每周/每日调整交给 `$xunji-cloud-coach` 与 Schedule。

## 安全边界

- 不作诊断、开药或替代医生建议。疼痛、晕厥、胸痛、明显气短等红旗优先于训练目标。
- 血压安全、睡眠和 HRV 判断必须遵循当前云端证据包，不能自创绝对阈值。
- 目标或安全边界需要实质变化时，重新运行本 Skill 并确认新的整体计划；不能让周微调静默改写总方向。
